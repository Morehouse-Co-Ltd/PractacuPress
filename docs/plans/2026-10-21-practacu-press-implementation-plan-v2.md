## 0. 一页结论

1. **企划书 v1.0 是一份完整的产品愿景，不是一份可执行的计划。** 它列出 29 个功能域、约 300 条细则，按当前单人（含 AI 辅助）投入估算约 180–220 人日；其中付费、打赏、广告、积分、插件市场五项占 60 人日以上，且与本项目"轻量、低配可跑"的立身之本直接冲突。
2. **项目实际进度已远超企划书的排期假设。** 企划书把"后端开发"排在 3–7 周，而仓库里身份、站点、内容、社区、媒体、审核、通知、消息、搜索、WebSocket、事件补偿十一条链路已完成并跑通，Rust 安全服务已接入，OpenAPI 契约已成型。真正的缺口不在"从零开发"，而在**面向读者的内容组织能力**（评论读取、分类、标签、SEO、订阅）与**可交付形态**（部署）。
3. **因此本计划不是"重做一遍"，而是"收口 + 补齐 + 上线"。** 12 周、约 47 人日、4 个阶段：先把当前系统变成**一个能对外访问的个人博客**（P0），再把创作体验做到企划书水准（P1），然后补内容组织与检索（P2），最后做运营配套（P3）。付费、广告、积分、插件市场明确移出 1.0。

**一句话：把 300 条愿景裁剪成 47 人日能交付的 1.0。**

## 3. 与企划书的差距分析

### 3.1 三个定位差异（必须先对齐，否则计划无从谈起）

| 维度 | 企划书 v1.0 假设 | 仓库实际 | 本计划的裁决 |
| --- | --- | --- | --- |
| 产品形态 | 单实例个人博客 | 多站点社区型 CMS（`site` 实体、成员角色、跨站隔离、审核流） | **保留多站点内核，个人博客作为"单站点 + 个人模式"的一种部署形态**。不退回单租户，因为多站点能力已沉没成本，且不影响单站体验 |
| 用户模型 | 作者 + 访客（游客可匿名评论） | 4 角色（平台管理员 / 站点管理员 / 编辑 / 成员）+ 匿名只读 | **匿名评论不进 1.0**。开放匿名写会引入验证码、频率限制、垃圾识别三条链路，成本高于收益；先做"登录可评"，个人博客场景由站长在设置里关闭评论 |
| 内容模型 | 文章 = 博客唯一内容 | `content_item` 以 `kind` 区分 article / post | **文章与帖子共用一张表**，前台默认只展示 article；帖子留给社区模式，不额外开发 |

### 3.2 技术选型差异

企划书 3.1 的选型表与实现存在系统性偏差。不是实现"跑偏"，而是企划书写于项目启动前，实现过程中做了更合适的选择。计划以现实为准，并在此备案：

| 层 | 企划书 | 实际 | 差异原因（保留哪个） |
| --- | --- | --- | --- |
| 前端框架 | React 18 | React 19 | 保留 19；无迁移成本 |
| UI 库 | Ant Design 5 | 无 UI 框架，自建 `styles.css` + 设计令牌 | **保留自建**。AntD 的运行时体积与"轻量"目标冲突，且现有页面已完成 |
| 构建 | Vite 5 | Vite 7 | 保留 7 |
| 后端框架 | Gin 1.10 | Gin 1.12 | 一致 |
| ORM | GORM 2.0 | Ent 0.14 | **保留 Ent**。类型安全 schema、生成式查询、迁移可控，优于 GORM 的运行时反射 |
| 认证 | JWT（未定算法） | Ed25519 + Refresh 轮换 + 重放检测 | **保留现状**，安全性显著高于企划书描述 |
| 密码 | bcrypt | Argon2id（Rust 服务） | **保留 Argon2id** |
| 缓存 | Redis 7（页面/数据/接口三层） | 无 Redis | **1.0 不引 Redis**。单机 SQLite + 进程内缓存足以支撑个人博客量级；引入 Redis 会让"零依赖部署"承诺失效 |
| 内容清洗 | 未提及 | 独立 Rust 服务，白名单 + 策略版本 | 保留，这是本项目最强的差异化能力之一 |
| 部署 | Docker Compose + Nginx | 仅 `dev.ps1` | **P0 补齐**，以 Compose 为唯一交付形态 |

## 4. 关键决策（ADR）

> 每条决策都写明"放弃了什么"，避免后续反复。

### D1 — 多站点内核不退回，个人博客是一种部署形态

**决策**：保留 `site` 实体与成员角色，个人博客 = 只有一个站点 + `site_kind = personal` + 关闭注册。
**放弃**：单租户模型带来的表结构简化。
**理由**：多站点能力已实现且有测试覆盖，回退等于重写权限层；单站部署下多站点逻辑零额外成本（Host 解析有单站例外分支）。

### D2 — 契约先行，前端不伪造端点

**决策**：任何新功能先改 `openapi.yaml`，再写领域层、存储层、路由、前端。
**放弃**：先做 UI 再补接口的"演示优先"路径。
**理由**：项目已有 37 条路径的契约与契约测试，破坏这个惯性会让前后端再次脱节；`ContentDetail.tsx` 的"评论读不回来"提示正是这条原则的正面样本——它诚实地暴露了缺口，而不是假装有数据。

### D3 — 编辑器用 CodeMirror 6，不自研富文本内核

**决策**：Markdown 编辑区换 CodeMirror 6（语法高亮、快捷键、括号匹配、粘贴图片），预览用现有 `lib/markdown.ts`；不做自研 WYSIWYG。
**放弃**：企划书 2.3.1 的"双模式自由切换（富文本 ↔ Markdown）"。
**理由**：自研富文本引擎是 3 个月量级的工程，且 Markdown ↔ 富文本双向无损转换是行业难题（Typora 级投入）。目标用户是技术创作者，Markdown 优先是正确取舍。富文本诉求用"粘贴 HTML 自动转 Markdown"覆盖 80% 场景。

### D4 — 搜索走 LIKE → FTS5 渐进路线，不引 Elasticsearch

**决策**：P2 在 SQLite 下条件启用 FTS5（`content_item_fts` 虚表 + 触发器），MySQL/PG 回退到 `LIKE`；统一在仓储层做接口抽象。
**放弃**：企划书未提但业界常用的独立搜索引擎。
**理由**：三方言约束 + 单机部署目标；FTS5 是 SQLite 内建能力，零额外进程。数据量超过 10 万篇再考虑外部引擎。

### D5 — 商业化功能整体移出 1.0

**决策**：付费阅读、付费下载、打赏、广告、积分等级、插件市场全部不做。
**放弃**：企划书 2.2.8、2.2.9、2.6、2.8、2.2.12 共约 60 人日的范围。
**理由**：
1. **合规成本**：支付需要商户资质、退款规则、发票与税务处理，个人开发者难以承担；
2. **安全成本**：付费内容防盗链、订单回调验签、权限校验是独立的安全面；
3. **产品一致性**：这五项与"轻量、零依赖、50MB 包体"的核心承诺互相矛盾——广告与积分需要额外的表、定时任务与前端组件。
**替代方案**：需要变现的用户，用"打赏"以外的外部方式（文末收款码图片）自行解决，平台不提供能力。

### D6 — 主题做配置化，不做代码级模板编辑

**决策**：保留现有 `SiteCustomization`（颜色、字体、首页 hero、布局令牌），增加 3–5 套预设；不提供在线编辑模板文件。
**放弃**：企划书 2.2.11 的"在线模板编辑 + 子主题 + 版本回滚"。
**理由**：在线编辑 Go 模板 / 前端组件等于给站点管理员开放代码执行面，安全边界无法收敛；且模板语法会成为永久兼容负担。

### D7 — Docker Compose 是唯一生产交付形态

**决策**：交付 `docker-compose.yml`（web + api + security 三服务，SQLite 卷挂载），附带 `.env.example` 与一页部署文档。
**放弃**：Windows 安装包（WiX）、Kubernetes 清单、Serverless 部署。
**理由**：目标用户是"有 VPS 的独立开发者"，Compose 覆盖 95% 场景；Windows 安装包需要签名证书与安装器测试，投入产出比低。

## 7. 技术方案要点

### 7.1 数据模型变更清单

| 表 | 变更 | 阶段 | 迁移风险 |
| --- | --- | --- | --- |
| `content_item` | + `cover_asset_id`、`pinned_at`、`view_count`、`seo_title`、`seo_description`、`og_image_asset_id`、`publish_at`、`access_password_hash` | P0/P1 | 低（全部可空/有默认） |
| `category`（新） | id、site_id、slug、name、description、cover_asset_id、sort | P0 | 低（新表） |
| `tag`（新） | id、site_id、slug、name | P0 | 低（新表） |
| `content_tag`（新） | content_id、tag_id（复合主键） | P0 | 低（新表） |
| `content_view`（新） | content_id、day、visitor_hash（唯一索引） | P0 | 低（新表） |
| `content_revision`（新） | content_id、revision_no、title、summary、body、created_by、created_at | P1 | 中（写放大，需上限 20 版） |
| `site` | + `seo`（JSON 或分列） | P0 | 低 |
| `audit_log` | 复用，不改 | — | — |

**迁移纪律**（沿用现有约定）：

1. 只新增表 / 可空列，禁止 drop column、drop index；
2. 每个迁移必须可重复执行（幂等），`migrate` 连跑两次结果一致；
3. 改 schema 后必须走 `scripts/gen.ps1` 重新生成 Ent 代码（直接 `go generate` 在 Windows 会因文件映射失败）；
4. 涉及数据回填的迁移（如 `view_count` 初始化）单独成文件，可回滚。

### 7.2 契约新增端点

**契约纪律**：

- 每个端点必须有：请求/响应 schema、错误响应引用（400/401/403/404/503）、OpenAPI 描述说明权限与副作用；
- 新增端点必须同步更新 `apps/web/src/lib/backend.tsx` 的 `Backend` 接口，否则前端无法调用；
- 契约测试（`packages/contracts`）必须在 CI 中阻断合并。

### 7.3 性能预算修订

企划书 1.3 的目标（首屏 ≤ 300ms、接口 ≤ 100ms、10 万 QPS、内存 ≤ 20MB、包体 ≤ 50MB）与当前架构不兼容：Go API + Rust 安全服务是**两个进程**，仅 Runtime 常驻就超过 20MB。以下为可测量、可验收的替代指标：

| 指标 | 企划书原值 | 本计划目标 | 测量方式 |
| --- | --- | --- | --- |
| API 常驻内存（RSS） | ≤ 20MB | ≤ 120MB（Go）+ ≤ 40MB（Rust） | `docker stats` 空载 10 分钟 |
| 接口响应 P95 | ≤ 100ms | ≤ 120ms @ 200 RPS（读接口，2C2G） | `hey -z 60s -c 50` |
| 首屏 LCP | ≤ 300ms | ≤ 1.2s（移动端 4G 模拟） | Lighthouse |
| 首页 TTFB | — | ≤ 200ms（同区域） | `curl -w` |
| 静态资源 | — | gzip/brotli + `max-age=31536000`（带 hash） | 响应头检查 |
| 单机承载 | 10 万 QPS | 500 并发读 / 50 并发写 | 压测报告 |
| 部署包体积 | ≤ 50MB | ≤ 80MB（含 web dist + 二进制） | `docker images` |

**扩容路径**（写进文档，不在 1.0 实现）：SQLite 写并发 > 50/s → 切 MySQL；单机 CPU 打满 → 前置 Nginx 缓存 + 多副本；搜索量级 > 10 万篇 → 独立 FTS 服务。

### 7.4 前端改造点

| 改造 | 位置 | 说明 |
| --- | --- | --- |
| 路由层补 head 管理 | `App.tsx` 或新增 `lib/head.ts` | 无 SSR，需运行时设置 title/meta/OG；爬虫依赖 sitemap 兜底 |
| 后端接口扩展 | `lib/backend.tsx` | 新增方法必须同时实现 `HttpBackend` 与 `DemoBackend`，否则演示模式崩溃 |
| 列表统一游标 | `lib/hooks.ts` | 现有分页与无限滚动两套逻辑合并为一个 hook |
| 侧边栏抽组件 | `components/Sidebar.tsx` | 首页/分类/标签/归档四处复用 |
| 编辑器替换 | `admin/Editor.tsx` | CodeMirror 6 按需引入语言包，控制包体 |

**包体纪律**：CodeMirror 6 + 语言包约 250KB（gzip 后约 80KB），必须走动态 `import()`，只在编辑器路由加载；首屏 JS 预算 ≤ 200KB（gzip）。

## 8. 质量门禁

### 8.1 单任务的完成定义（DoD）

每个任务必须同时满足：

1. **契约先行**：OpenAPI 已更新，schema 完整，错误码齐全；
2. **领域测试**：核心规则有单元测试（状态迁移、权限边界、幂等）；

6. **文档同步**：涉及运维/使用的变更更新 README 或 `docs/`。
